Overview

invoi is an AI-powered invoice management dashboard for small Saudi businesses: users upload incoming invoices, invoi stores and organises them, and flags the ones that need a human check. This document describes the system as it is on the develop branch of JxTechStudio-org/invoi (last merge 22 Oct 2026, PR #113). main was brought level with develop the same day (PR #114), so everything described as built here is on the production branch.

Problem. Businesses that receive many invoices a day (100+ from different vendors and payment methods) re-type vendor, amount, date and tax by hand. It is slow and error-prone.

Users. Small business owners and accountants without a dedicated finance team.

Scope of this version. Incoming invoices only (expenses the user receives from vendors). The customer on every invoice is therefore always the account owner, identified by User.businessName. Arabic and English invoices are both first-class.

What works today: sign-up and login (JWT), upload of PDF/JPEG/PNG to object storage, invoice list with search, status and date filters and CSV export, invoice detail with a preview of the original file, manual editing of all 13 editable fields, approve and report-error actions, delete with confirmation, the review rules, dashboard and vendors pages, health and Prometheus metrics, and a Jenkins pipeline that tests and deploys on every build.
What does not exist yet: the AI extraction itself. Uploaded invoices stay in processing with empty fields until someone fills them in by hand. Section 8 is the agreed extraction design, section 10 the analytics and n8n design, and section 9 records every decision behind both.

Architecture

One container serves both the API and the web app; PostgreSQL holds invoice data and RustFS holds the original files. n8n sits outside the app and only talks to it through webhooks: the app sends one user's data, n8n calls back with the result (section 10). Power BI becomes downloadable templates and no longer reads the database. Extraction will run inside the same container as a background job (decision C10); the only new outside dependency is the Anthropic API.

Invoice lifecycle

Today steps 1, 2, 4 and 5 run. Step 3 is missing, so the rules only fire when a user saves an edit, and a manually filled invoice reaches completed only through approve. With extraction, a clean result goes straight to completed; anything flagged waits for a human. The three statuses stay processing, needs_review and completed; no new status is needed.

Rules worth knowing

  • Upload: PDF, JPEG or PNG, up to 10 MB (MAX_UPLOAD_SIZE_BYTES). One file per request. The invoice is created with status processing and no extracted fields.
  • Search matches vendor name, invoice number and customer name, case-insensitive.
  • Edit (PUT): any of vendorName, invoiceNumber, invoiceDate, dueDate, totalAmount, taxAmount, amountPaid, currency, paymentStatus, paymentMethod, customerName, taxNumber, crNumber; at least one field. Amounts are non-negative with up to 2 decimals. Sending null clears a field. status cannot be set directly. The frontend form sends only changed fields and checks due date ≥ invoice date.
  • Approve: 400 unless vendorName, totalAmount and invoiceDate are set; then completed and all reasons cleared, even if rules had fired. A total of zero is allowed.
  • Flag: adds user_flagged, which survives edits and is cleared only by approval. An invoice in needs_review stays there after its flags are fixed until someone approves it.
  • File: Content-Type comes from the stored extension, never from stored metadata; served inline with nosniff and no-store. Local storage refuses symlinks and directories. Demo invoices with seed:// references have no stored file: the file returns 404 and delete removes only the row (PR #113). The frontend fetches the file with the token as a Blob.
  • CSV export: UTF-8 with BOM so Excel shows Arabic correctly. Cells starting with = + - @ are prefixed with ' to block formula injection.
  • Register validation: password 8+ characters with upper, lower, digit and symbol; phone +9665 + 8 digits; names in Arabic or English letters; email unique (409 if taken).
  • Rate limits: 60 requests per minute per IP, 10 per minute on login and register. Express trusts exactly one proxy hop, so req.ip is the address Nginx saw and a forged X-Forwarded-For no longer resets the login budget.
  • Errors come back as JSON through a global exception filter, which logs every 5xx with its stack. A 401 makes the frontend clear the token and send the user to /auth/login?reason=session_expired. Logout clears the React Query cache and in-memory notifications; login clears the cache.
Endpoints the frontend still expects: forgot/reset password (the page now says the feature is not available yet), settings (English business name, reviewAmountThreshold), and JSON dashboard metrics (the dashboard calls GET /metrics, which returns Prometheus text).

AI extraction: Phase 1 design

The review rules are built; the extraction that should feed them is not. This section is the agreed design from the 21 Oct 2026 decision round, with the 22 Oct amendments. Section 9 lists each decision with its code (A1, B6, …) so it can be traced from here.

The 12 fields to extract: vendor name, invoice number, invoice date, due date, total amount, tax amount, currency, payment status, payment method, customer name (as printed), vendor tax number, vendor CR number. Line items are out of scope.

How it runs

  1. Queue. Upload creates the invoice and an ExtractionJob row in the same transaction. A worker inside the NestJS process claims jobs with SELECT … FOR UPDATE SKIP LOCKED, one or two at a time. No Redis: under 200 invoices a day this is enough (A5, C10).
  2. Kill switch and budget. Before each call the worker checks EXTRACTION_ENABLED, the account allow-list and the month's spend (sum of extractionCostUsd). At the cap it stops, leaves jobs queued and logs an alert; nothing is lost (A4, G25).
  3. ZATCA QR first. Decode the QR (TLV, Base64) from the image, or from rendered PDF pages. Tags 1–5 give seller name, VAT number, timestamp, total with VAT and VAT total. Decoded values get score 1.0 once they pass the checks (B7).
  4. Model for the rest. One call to Claude Sonnet 5.5 with the file and a fixed JSON schema for all 12 fields; QR values are passed in as known. Payment status and method only when clearly printed; anything not on the page comes back null (A1, A2, F23).
  5. Normalise. Arabic-Indic digits and the Arabic decimal separator to ASCII; dates to ISO; currency to the enum. Hijri dates are not converted: the field is left empty with a low score so a human enters it (F20, F21, F22).
  6. Check and score each field with code (below), then run the review rules. Clean result: completed. Any rule fires: needs_review with reasons (B6, X1).

Confidence: checks done by code

Each field starts at 1.0 and loses score for every failed check; below 0.90 triggers low_confidence. The model's own view is not trusted as a score (B6).

Failure, retries and re-extraction

  • Retries: 3 attempts with growing gaps (about 1 min, 5 min, 15 min). Then needs_review with extraction_failed, and the user fills the fields in by hand (C11). A file that is clearly not an invoice fails at once, without retries.
  • Re-extract button on the detail page calls POST /invoices/:id/extract. Fields in editedFields are never overwritten; every PUT adds the fields it changed (C12).
  • Existing invoices: a one-time backfill queues every invoice still in processing with empty fields, within the monthly budget, and only for accounts listed in EXTRACTION_ACCOUNT_ALLOWLIST. It does not run while the allow-list is empty, and the demo account is always skipped (C13, amended 22 Oct).

Frontend during extraction

  • Polling: every 5 seconds on GET /invoices/:id/status, only on pages showing a processing invoice, stopping after 2 minutes. On the list page one list refetch replaces per-row polling. 12 requests a minute stay well inside the 60/min limit (D14).
  • While processing: the user can view the invoice and its file, but edit, approve and report error are disabled, with a short Arabic note. The backend enforces the same with 409 (D15).
  • New reason labels in Arabic for extraction_failed, zero_total, tax_over_30_percent and multiple_invoices in invoiceLabels.ts.
  • Settings page: English business name and review threshold, via PATCH /auth/me (F19).

Data, privacy and cost

  • Outside KSA is allowed on one condition: zero data retention at the provider. Confirm it in writing with Anthropic for this account before the first real invoice is sent; until then, test only on the anonymised test set (E16).
  • Account: JX Tech Studio company account. Key ANTHROPIC_API_KEY in /run/secrets/invoi.env, like JWT_SECRET (A3).
  • Stored per invoice: model, duration and cost. The raw response is not stored (E17).
  • Upload limit unchanged: 10 MB, one file per upload; multi-file upload later (E18).
Budget is the tightest constraint. The cap is USD 2 a month until the project gets its own budget (A4), shared with the analytics AI (H2). At an estimated USD 0.01 per one-page invoice on Sonnet 5.5 that is about 200 invoices a month, against an expected volume of up to 200 a day. The model comparison (about 50 invoices on Sonnet and 50 on Haiku, roughly USD 0.55) and the backfill also come out of it. Real costs must be measured on the test set; raise the cap before inviting more than one or two accounts.

Measuring accuracy and rolling out

  • Test set: Jana prepares 30–50 real invoices with their correct values: Arabic and English, PDFs and phone photos, some poor scans, some with Arabic-Indic digits, with sensitive data removed (B9).
  • Comparison: a script runs the set on Sonnet 5.5 and Haiku 5.5 and reports field accuracy, cost and time per invoice. Proposed target: 95% of fields correct on clear PDFs. Accuracy is still not a hard MVP requirement.
  • Rollout: one or two accounts first through the allow-list; the team checks the first ~100 extracted invoices before wider release (G25, G26).

Definition of Done for the MVP: an upload moves through extraction to completed or a reviewable state, all 12 fields are shown, the flags fire per the rules above, and the user can correct and save any field.

Analytics, n8n and Power BI

Design agreed on 21 Oct 2026 (decisions H1–H11 in section 9). n8n does the analysis and the AI writing; the backend owns identity, data and budget. n8n no longer connects to PostgreSQL, and Power BI no longer reads the production database. Owners: Danah (analytics page, frontend and backend), Abdullah (n8n workflows, Power BI templates).

Rules

  • Endpoint: POST /analytics. The two team guides disagree (/analytics vs /invoices/analysis); this document uses the former, as its own Nest module.
  • Request: preset buttons only; the free-text question waits until isolation and cost are proven (H3). The button list comes from Abdullah's workflows.
  • Data sent: only fields the analysis needs, for invoices not in processing: vendor, number, dates, paidAt, amounts, currency, payment status, status (H6).
  • Limits and cache: 5 analyses per user per day; the same type within an hour returns the stored result at no cost; the latest result per type is shown when the page opens (H10).
  • Cost: the AI node uses Claude through the company Anthropic account, with zero data retention, inside the same monthly cap as extraction. n8n returns costUsd with each result (H2).
  • Currencies: with 13 currencies, sums are grouped by currency, never added across them.
  • States on the page: empty, running (button disabled, 20–60 s expected), result, error with "try again".

Demo account in production

The account with 2,000 fake invoices stays in production and is marked with User.isDemo (H9). It is excluded from extraction, backfill and scheduled runs, but buttons work on it for testing. Power BI: templates sold with a paid plan

Power BI stops reading the database (H11). Each report becomes an empty template (.pbit) that users on a plan that includes Power BI can download; they load their own data, usually the CSV export. This needs:

  • The CSV export to carry every column the templates use. Today it lacks amountPaid, paidAt, status and the upload date, so unpaid ratio, aging and DPO cannot be computed from it.
  • A plan on the account and a download endpoint gated by it. Plans and billing do not exist yet.
  • Templates on the brand colours (#10B981, #047857, #0F172A) and Arabic labels.
Remove direct database access once the webhooks are live: the Postgres accounts used by n8n and Power BI (such as powerbi_reader) can see every company's invoices.

Infrastructure and deployment

invoi runs as three Docker Compose services on one server behind the host's Nginx, which terminates SSL for invoi.jxtechstudio.com and proxies to the app on 127.0.0.1:3016. Every port is bound to localhost; only Nginx is public. The app trusts exactly one proxy hop, so Nginx must stay the only proxy in front of it.

ServiceImageHost portVolume
app (invoice-app)Built from Dockerfile, Node 22 alpine, runs as node127.0.0.1:3016 → 3000invoiproject_invoice_uploads (legacy files)
postgres (invoice-postgres)postgres:16127.0.0.1:5433 → 5432invoiproject_postgres_data
rustfs (invoice-rustfs)rustfs/rustfs:1.0.0-rc.6127.0.0.1:9001 (console)invoiproject_rustfs_data

The app waits for healthy Postgres and RustFS, then runs prisma migrate deploy and starts. Migrations therefore apply automatically on every deploy, including the Phase 1 migration. The extraction worker runs in the app container and needs outbound HTTPS to the Anthropic API.

Jenkins pipeline (Jenkinsfile, one build at a time, env file at /run/secrets/invoi.env)

  1. Build — validate the Compose file, build the app image.
  2. Lint — ESLint on the backend.
  3. Test — npm run test:e2e inside the app image (15 Jest suites: lifecycle, ownership, review, approval, CORS, storage, metrics, proxy rate limit, exception filter). Extraction tests must mock the model call: CI never spends budget.
  4. Deploy — docker compose up -d --build app postgres, check both containers run, then call /api/health up to 5 times.

The frontend has no lint or test stage yet.

Monitoring. /api/metrics exposes invoi_http_requests_total (by method, route and status code) plus Node.js defaults for Prometheus and Grafana. It is public: restrict it to the Prometheus host in Nginx. Unexpected errors reach the container log with their stack. Phase 1 adds extraction counters (jobs by outcome, spend this month).

Not in place yet: scheduled backups of the Postgres and RustFS volumes, a written restore procedure, and the Nginx config in version control.

Developer guide

A new developer can run invoi locally in about 15 minutes with Node 22 and Docker.

Run it locally

git clone https://github.com/JxTechStudio-org/invoi.git && cd invoi
git checkout develop
cp .env.example .env              # fill in passwords, JWT_SECRET and RustFS keys

# Database and storage only
docker compose up -d postgres rustfs

# Backend on http://localhost:3000/api
cd backend && npm ci
# DATABASE_URL=postgresql://<user>:<pass>@localhost:5433/<db>
# RUSTFS_ENDPOINT=http://localhost:9000 (map port 9000 in Compose for local use)
# EXTRACTION_ENABLED=false unless you are working on extraction
npx prisma generate && npm run prisma:migrate:deploy
npm run start:dev

# Frontend on http://localhost:5173
cd ../frontend && npm install
VITE_API_BASE_URL=http://localhost:3000/api npm run dev

Or run the whole stack exactly as production: docker compose up -d --build, then open http://127.0.0.1:3016.

Git workflow

  • main is production; Jenkins deploys it. develop is the integration branch.
  • Branch from develop as feature/<name>, fix/<name> or docs/<name>, and open the PR into develop.
  • develop is merged into main by PR once it is green. As of this version the two are in sync (PR #114, 22 Oct).
  • Schema changes always ship as a new Prisma migration; never edit an applied one.

Conventions

  • Backend: one Nest module per domain; validate every input with a DTO; scope every invoice query by userId.
  • Frontend: code goes in features/<area>/{api,components,hooks,pages,constants}; shared UI in features/shared; colours from theme tokens, never hex.
  • Text in the UI is Arabic and right-to-left; code, commits and PR titles are in English.
  • Never call the paid model from tests or CI; mock the client.
  • The repository has 41 remote branches; delete a branch once its PR is merged.
  • This document lives in docs/technical-documentation/; change it in the same PR as the code it describes.
